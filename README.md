# Utility Payments — A/B Test Product Analytics

Учебный pet-проект по продуктовой аналитике на примере A/B-тестирования новой формы оплаты ЖКХ.

Цель исследования — проверить, связана ли упрощённая форма оплаты с ростом конверсии от открытия формы до успешного платежа.

**Статус:** исследовательский проект. Все выводы относятся к предоставленному датасету и не являются оценкой финансового эффекта продукта.

## Что исследуем

В рамках проекта разбираются следующие вопросы:

- Насколько качественны исходные данные и корректно ли связаны пользователи с платежами?
- На каких этапах воронки теряются пользователи?
- Отличается ли конверсия между группами A и B и насколько статистически убедителен результат?
- Сохраняется ли эффект при альтернативных способах анализа?
- Как различается результат в сегментах по устройствам, городам и возрасту?
- Какие дополнительные данные нужны для принятия продуктового решения?

## Запуск проекта

Нужен Python 3.10 или новее.

Установить зависимости:

```bash
python -m venv .venv
```

Windows:
```bash
.venv\Scripts\activate
```

macOS/Linux:
```bash
source .venv/bin/activate
```

```bash
pip install -r requirements.txt
jupyter lab
```

Ноутбуки рекомендуется запускать последовательно:

1. **01_data_audit** — исследование исходных данных, проверка качества и формирование витрин.
2. **02_funnel_analysis** — анализ платёжной воронки, повторных попыток и времени прохождения этапов.
3. **03_ab_test_analysis** — проверка основной гипотезы, статистические тесты, доверительные интервалы, SRM и MDE.
4. **04_segmentation_analysis** — сравнение результатов по устройствам, городам и возрастным группам.
5. **05_robustness_and_recommendation** — проверка устойчивости результатов и формулирование продуктовой рекомендации.
6. **06_methodological_robustness** — дополнительные проверки методологии, альтернативные статистические подходы и анализ чувствительности выводов.

## Данные и методология

В эксперименте пользователи случайным образом распределялись между группами A и B. Поэтому основной единицей анализа является пользователь, а не отдельная попытка оплаты.

В проекте используются две витрины:

- пользовательская — одна строка на клиента;
- платежная — одна строка на попытку оплаты.

Основная метрика — доля пользователей, совершивших хотя бы одну успешную оплату, среди открывших форму. Дополнительно рассчитывается ITT-конверсия по всем пользователям с известной экспериментальной группой.

Повторные попытки сохраняются, а для анализа платежных событий учитывается зависимость нескольких попыток одного пользователя.

При подготовке данных группа из таблицы пользователей считается источником истины. Некорректные значения возраста не приводят к исключению пользователя из основного анализа. Записи без идентификатора пользователя и клиенты без экспериментальной группы обрабатываются отдельно.

## Основные результаты

По итогам анализа получены следующие результаты:

| Метрика | Группа A | Группа B |
|---|---:|---:|
| Успешно оплатили | 494 | 603 |
| Открыли форму | 751 | 750 |
| Конверсия | 65,8% | 80,4% |

Разница составляет **+14,6 п.п.**, относительный прирост — около **22%**.

95% доверительный интервал разницы: +10,2…+19,0 п.п. Результат двустороннего z-теста: p = 1,7 · 10⁻¹⁰.

Дополнительные проверки показали:

- Направление эффекта сохраняется при ITT-анализе и анализе первых попыток.
- Скорректированная логистическая регрессия также показывает положительный эффект.
- Перестановочный тест и байесовская оценка поддерживают основной результат.
- Проверка устойчивости показывает, что для потери статистической значимости потребовалось бы изменить статус 75 успешных оплат в группе B.
- Наибольшая разница в воронке наблюдается между вводом реквизитов и подтверждением платежа.
- Все 12 вторичных сегментных оценок положительны, 9 остаются значимыми после поправки Холма. При этом статистически значимых взаимодействий с устройством и городом не обнаружено.

### Итоговая рекомендация

Результаты поддерживают запуск новой формы, однако я бы рекомендовал делать это постепенно: сначала 25% пользователей, затем 50% и далее 100%, сохраняя контрольную группу на уровне 5–10%.

При масштабировании необходимо следить за защитными метриками. Финансовый эффект эксперимента оценить нельзя: в исходных данных нет информации о суммах платежей, марже и затратах.

## SQL и дополнительные материалы

SQL-запросы написаны для DuckDB. Они позволяют работать с подготовленными витринами и рассчитывать основные продуктовые метрики.

Основной результат исследования — двухстраничный отчёт. Также в проекте предусмотрены Markdown-версия отчёта, JSON с результатами методологических проверок и графики.

Материалы, содержащие реальные данные или результаты, по которым можно восстановить конфиденциальную информацию, остаются локально и не публикуются.

## О проекте

Проект объединяет работу с данными, продуктовые метрики, анализ воронки, A/B-тестирование и проверку устойчивости результатов. Основной акцент сделан не только на статистических расчётах, но и на их интерпретации и использовании для принятия продуктовых решений.
